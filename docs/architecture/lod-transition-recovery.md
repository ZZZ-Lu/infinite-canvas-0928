# LOD 切换的渐进加载

## 本轮修改

1. 文字排版采用模块级 LRU 缓存，最多 128 项、总键长不超过 500000 字符。相同提示词/宽度/字体跨卡片、跨 LOD 卸载复用。
2. 文字和面板位图采用共享 LRU 缓存，估算 RGBA 上限 32MiB、最多 64 项。超限淘汰并清空旧画布缓冲；资源未完成的参考图面板不写入缓存。该预算不等同于浏览器总显存。
3. 挂载与绘制共用 scheduleCanvasSurface，交互期间暂停，一个绘制/挂载任务后留出显示机会；取消会解除正在等待的挂载 Promise。
4. ProgressiveGenerationCard 逐卡订阅渲染准入状态，放行一张卡片不再调用 App 顶层 React 状态更新。该组件只决定渲染，不修改卡片业务模型。
5. 高 LOD 面板首次文字和装饰都绘制完成后才整体显示，低 LOD 占位继续保留。Nano 层同时检查媒体和面板就绪状态，不再仅凭图片完成就交接；800ms 固定退出定时器已移除。

恢复起点仍为 300ms。完整卡片的 React 挂载及单个绘制任务不可抢占，因此统一队列不是严格的每帧耗时上限。

## 验证

- TypeScript 检查与生产构建通过。
- tests/canvas-performance 下的验证脚本覆盖共享队列取消/暂停/恢复、位图预算和 LRU 淘汰、逐卡通知与取消订阅。
- 浏览器低高 LOD 切换后，18 张卡片和 18 块面板均完成显示。
- 临时 rAF 采样记录了交互及 DOM 活动窗口，最新一次样本 p95 为 8.5ms，但最大间隔约 133ms，仍存在长帧。采样时长不同且没有严格的修改前对照，不据此计算收益百分比或保证最低 FPS。
- 临时测量脚本已移除，正常预览重新启动。

后续需要用 React Profiler 和 Long Animation Frame 定位剩余峰值，不能将恢复后 120 FPS 等同于整个切换过程稳定。

## 自适应节奏

`canvasRecoveryPolicy.ts` 根据最近 60 个有效帧间隔中的最快值估计刷新节奏（约 60–240Hz），避免把掉帧后的平均值当成目标帧率。启动先校准 12 帧，正常 60Hz 间隔不会被误判为 120Hz 丢帧。

任务同步耗时超过半个帧预算，或后续 rAF 间隔明显变长时，增加空闲帧。后续间隔包含 React 提交、布局和其它主线程工作。队列暂时空时仍采集一个尾帧。连续稳定 18 帧后只减少一级间隔，避免反复加速减速。

每个任务之间保留 0–12 个空闲帧，始终一次一个任务；即使持续繁忙也有有限等待，不无限停止加载。手势期间仍暂停，恢复起点仍为 300ms。它是负反馈节流，不能抢占正在运行的单张卡片挂载或保证消除所有长帧。

自适应状态只存在于渲染调度器，不写入项目文件。新增模拟验证覆盖 60/120Hz 校准、同步任务和延迟帧降速、缓慢提速、持续繁忙时进度、手势暂停和取消恢复；类型检查与生产构建通过。

## 数据与渲染边界

缓存位图、就绪集合和准入订阅均为 renderer 局部内存；不存入项目模型，不参与持久化。业务卡片、世界坐标、原始 AI 输入、项目 JSON 格式不变。DOM 依赖仅在排版和绘制适配器；未来更换 Canvas/WebGL 时替换这些适配器与准入组件即可，业务命令不需依赖 DOM。

稳定时每帧最多一个任务。新手势结束后旧的空闲帧数最多保留 2 级，随后重新根据当前负载调整；卡片准入后的额外固定等待缩短为一次 rAF。300ms 恢复起点不变。
